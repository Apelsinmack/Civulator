# 1. AI / Reinforcement Learning Improvements

## 1.1 DQN Quick Wins

These three changes address your known issues directly and could resolve both training
plateaus and high draw rates. Each is a few lines of code.

### Target Network (your #1 known issue)

A frozen copy of the Q-network, updated every N steps, used to compute TD targets.
Without it, the network chases its own changing predictions — the "moving target"
problem. This is almost certainly your single biggest source of training instability.

```python
# Implementation: ~10 lines
target_net = copy.deepcopy(policy_net)
target_net.eval()

# Every 1000 steps:
target_net.load_state_dict(policy_net.state_dict())
# Or soft update: for tp, pp in zip(target_net.parameters(), policy_net.parameters()):
#     tp.data.copy_(0.005 * pp.data + 0.995 * tp.data)
```

### Double DQN (one-line change on top of target network)

Use the online network to *select* the best action, but the target network to
*evaluate* it. Fixes systematic overestimation of Q-values — particularly harmful
in strategy games where many actions are similar quality.

```python
# Instead of: max(Q_target(s'))
# Use:        Q_target(s', argmax(Q_online(s')))
next_actions = policy_net(next_states).argmax(1)
next_q = target_net(next_states).gather(1, next_actions.unsqueeze(1))
```

### Epsilon Decay (currently fixed at 0.3)

Fixed epsilon means the agent never transitions from exploration to exploitation.
This directly contributes to high draw rates — the agent keeps making random moves
even after learning good strategies.

```python
epsilon = max(0.05, 1.0 - step * (1.0 - 0.05) / 50000)
```

## 1.2 Rainbow DQN Components Ranked

The Rainbow DQN paper (Hessel et al., 2018) combined six DQN extensions and
ablated each one. Here they are ranked by impact for a strategy game like Civulator:

### Tier 1 — High Impact, Low Effort

| Component | What It Does | Effort | Why It Matters |
|-----------|-------------|--------|----------------|
| **Target network** | Stabilizes TD targets | ~10 lines | Fixes your #1 issue |
| **Double DQN** | Fixes Q-value overestimation | 1 line change | Prevents fixation on lucky estimates |
| **Epsilon decay** | Explore early, exploit later | 1 line | Fixes your #2 issue |

### Tier 2 — High Impact, Moderate Effort

| Component | What It Does | Effort | Why It Matters |
|-----------|-------------|--------|----------------|
| **Prioritized Replay (PER)** | Replay surprising transitions more | ~150 lines (SumTree) | Most impactful single Rainbow component in ablation. Rare decisive moments (battles, captures) get replayed more |
| **N-step returns (n=3-5)** | Look ahead n steps for TD target | ~50 lines buffer mod | Second most impactful in ablation. Propagates reward signal faster — crucial for delayed-reward strategy games |
| **Dueling architecture** | Separate V(s) and A(s,a) streams | ~20 lines arch change | Learns "this state is good/bad" separately from "this action is better/worse." Very natural for strategy games |

### Tier 3 — Nice to Have

| Component | What It Does | Effort | Notes |
|-----------|-------------|--------|-------|
| **Noisy Nets** | Learned exploration noise | ~50 lines | Replaces epsilon scheduling. Not critical for small networks |
| **Distributional (C51)** | Learn full return distribution | High | Important in Atari ablation but adds significant complexity. Skip for now |

## 1.3 Reward Shaping

### Potential-Based Reward Shaping (PBRS) — Theory-Safe

Ng et al. (1999) proved that adding `F(s,s') = gamma * Phi(s') - Phi(s)` preserves
the optimal policy. The agent learns the same thing, just faster.

Good potential functions for Civulator:
- `Phi(s) = own_units - enemy_units` (army advantage)
- `Phi(s) = own_cities * 50 + own_units * 10` (weighted score)
- `Phi(s) = sum(own_unit_HP) - sum(enemy_unit_HP)` (health advantage)
- `Phi(s) = territory_controlled` (tiles closer to your units)

Because PBRS uses a *difference* of potentials, it rewards *improvement*, not
absolute state. Very easy to implement (~5 lines).

### Win/Loss Reward Design

Current setup presumably gives reward only at game end. Improvement:
- **Win = +1, Loss = -1, Draw = -0.5**
- Making draws slightly negative incentivizes playing for a win rather than a safe draw
- This directly addresses the high draw rate
- Alternatively: margin-of-victory reward (score difference at end)

### Dense Reward Components (use carefully)

These can distort the optimal policy if too large. Keep magnitudes small:
- +0.1 per tile explored
- +2 for damaging enemy unit (not just killing)
- +5 for building a unit
- +0.1 per turn per city owned
- -0.01 per turn (small time pressure)

## 1.4 Self-Play and Multi-Agent Training

### Basic Self-Play with Opponent Pool (Recommended Starting Point)

1. Train agent for N episodes against a random/scripted opponent
2. Save checkpoint
3. Train against a mix: latest checkpoint (70%), random past checkpoint (20%), random policy (10%)
4. Repeat

This prevents **strategy cycling** (A beats B, B beats C, C beats A) and produces
robust agents. Track Elo rating over training to measure real improvement.

### Population-Based Training (PBT)

Train multiple agents with different hyperparameters simultaneously. Periodically,
worse agents copy weights + mutated hyperparameters from better agents. Great for
automated hyperparameter tuning but requires running many parallel training runs.
May be too expensive for a single RTX 3070.

### League Training (StarCraft/AlphaStar Style)

Maintains a league with main agents, exploiters, and league exploiters. Produces
the most robust agents but requires massive compute. Overkill for Civulator.

**Practical takeaway**: The key insight from league training — training against a
*diverse* set of opponents prevents strategy collapse — can be achieved with the
simple opponent pool approach above.

## 1.5 Alternative Algorithms

### PPO — The Industry Workhorse

PPO (Proximal Policy Optimization) is what OpenAI Five used for Dota 2 and what
most modern game AI uses. Advantages over DQN for strategy games:
- More stable training (no replay buffer staleness)
- Better with self-play (on-policy = always training against current opponent)
- Works well with recurrent networks (LSTM memory)
- Handles large action spaces more naturally

Downside: less sample-efficient (needs more environment steps). But if your
environment is fast, this doesn't matter.

**Effort**: Moderate rewrite (~200 lines core), or use Stable-Baselines3's PPO with
a custom Gymnasium environment wrapper.

### AlphaZero-Style MCTS + Neural Network — The Gold Standard for Board Games

AlphaZero was designed *exactly* for turn-based, perfect-information, two-player
games. Civulator is close to this. Key components:
- Neural network outputs: policy head (move probabilities) + value head (win probability)
- MCTS uses the network to guide search
- Self-play generates training data
- Dominates all pure RL approaches for board games

**Effort**: High. MCTS is ~300-500 lines. Training loop is fundamentally different from DQN.
But there are great reference implementations:
- **alpha-zero-general** (GitHub: suragnair/alpha-zero-general) — clean, extensible
  Python implementation for arbitrary board games

**My assessment**: If you want the *best possible AI*, AlphaZero is the way to go.
But it's a bigger project than improving DQN. The DQN quick wins should come first.

### Others

- **A2C/A3C**: Simpler than PPO, good baseline. Essentially PPO without clipping.
- **SAC for discrete**: Works but no clear advantage over PPO/DQN for board games.
- **IMPALA/R2D2**: Designed for 100+ machines. Way overkill for single-GPU.
- **R2D2's ideas** (LSTM + burn-in) are useful independently of the distributed infra.

## 1.6 Action Space Design

### How AlphaStar Handles Large Action Spaces

AlphaStar uses auto-regressive action decomposition:
1. Action type (move, attack, build)
2. Unit selection (pointer network over entities)
3. Target location (spatial output via deconvolution)
4. Target unit (another pointer network)

Each sub-action is conditioned on previous ones:
`P(a) = P(type) * P(unit|type) * P(location|type,unit)`

Your Select-and-Move is a simplified version of this.

### Options for Civulator

**Option A: Properly Condition Move on Select (Easiest)**
Ensure the destination network receives information about which unit was selected
(unit type embedding, position encoding). Verify this is happening. (i think this IS happening - erik)

**Option B: Flat Action Space with Masking**
Output policy over all (unit, destination) pairs. Mask illegal combinations.
For 4x8 grid with ~10 units: ~320 possible actions. Very manageable.
Cleaner than two-step and avoids credit assignment issues. (i'm not really drawn to this solution, i hope we can scale the games to be at least 12 or perhaps 24 players. It would even be cool to simulate 100 players on the world map.

**Option C: Merge Build Agent into Main Agent**
Each turn, agent either commands a unit (select + move) or issues a build order.
Unified approach prevents coordination issues between two independent agents. - Erik comment: I like tha alpha star method with assigning target locations - then have a pointer network to target specific units. Strategy vs Tactic, can be done by two different networks.

### Action Masking Reference
Huang & Ontanon (2020): "A Closer Look at Invalid Action Masking in Policy Gradient
Algorithms." Set logits to -inf for illegal actions before softmax. Critical and
well-supported in both DQN and PPO. Commennt: This is something we should jsut implement

## 1.7 State Representation Ideas

### Enriched Channel Design (Low-Hanging Fruit)
Ensure input channels encode:
- Per-tile: terrain (one-hot), resources, fog of war
- Per-unit: type (one-hot), HP, owner, has-moved-this-turn
- Per-city: owner, population, current production, turns-to-complete
- **Global features**: turn number, relative score, total units per player — broadcast
  as constant channels across all spatial positions (this is what AlphaStar does) - let's do the same!

### Hex-Aware Convolutions
Standard square convolutions don't perfectly respect hex adjacency. Options:
- **HexaConv** (Hoogeboom et al., 2018): Specialized hex convolution kernels that
  connect only to the 6 hex neighbors. ~50 lines for the kernel.
- **Offset-corrected padding**: Shift odd/even rows before convolution. Simple and effective. Comment: I am aware of this, i thought i'd implement it at some point, but has pushed it to the future. Wonderful that someone else has all ready done it. we sohuld too! 

### Graph Neural Networks
Treat each hex as a node, edges = adjacency. Message-passing GNN (GraphSAGE, GAT).
Naturally handles hex topology. But slower than CNNs for regular grids and adds
PyTorch Geometric dependency. Not worth it for 4x8, might matter for larger maps.

### Transformers / Attention
Treat each tile or unit as a token. Self-attention captures long-range dependencies
that CNNs miss. But for a 4x8 = 32 tile grid, a 2-3 layer CNN already has full
receptive field. Consider for larger maps or better unit-unit interaction modeling.

 Tokens as vectors                                                                                               
  A token is just a vector that represents one thing. In language models, each word is a token → a vector. In your   game, each hex tile could be a token → a vector encoding everything about that tile:

  Tile (3, 5) → [terrain=hills, own_warrior_hp=0.8, enemy_archer_hp=0.0, city=none, ...]

  So for a 4x8 grid, you'd have 32 tokens, each being a vector of, say, 25 features (your channel count). That's a
   matrix: [32 x 25].

  What attention does

  Now here's where your basis vector intuition connects. In a CNN, each tile only "sees" its neighbors (the kernel
   size). Tile (0, 0) doesn't know what's happening at tile (3, 7) until the signal propagates through multiple
  layers.

  Attention asks a different question: "For each tile, which other tiles are relevant to it?"

  It works through three projections — and this is where your linear algebra intuition is spot on. Each token gets
   projected into three different vector spaces:

  - Query (Q): "What am I looking for?" — the tile asks a question
  - Key (K): "What do I contain?" — every tile advertises its content
  - Value (V): "What information do I carry?" — the actual payload

  Attention(Q, K, V) = softmax(Q @ K^T / sqrt(d)) @ V

  The Q @ K^T is literally a dot product between every pair of tiles — measuring similarity/relevance. The softmax
   turns it into weights. Then you take a weighted sum of Values.

  So each tile's output is a weighted combination of all other tiles' information, where the weights are learned
  based on content. Tile (0, 0) with your warrior can directly attend to tile (3, 7) with the enemy city and think
   "that's relevant to me" — in a single layer, no propagation needed.

  Your basis vector analogy

  You're not far off. The Keys form something like a set of basis directions in an abstract space. Each Query
  projects onto those directions to find which Keys it aligns with. The difference from a traditional basis is
  that the "basis" (the Keys) changes with every game state — it's content-dependent. The network learns what
  questions to ask (Q projection) and how to advertise content (K projection) such that strategically relevant
  tiles attend to each other.

  In concrete Civulator terms: a warrior token might learn a Query that means "where are nearby enemies?" and
  enemy units would have Keys that match that Query strongly. The attention weight would be high between them, so
  the warrior's output representation would include information about those enemies — regardless of distance on
  the map.

  When it matters vs CNN

  For your 4x8 grid: a CNN with 2-3 layers already covers the entire map (receptive field = full grid). Attention
  wouldn't add much.

  For a 32x64 grid with 100 units across 12 players? A CNN would need many layers to propagate information across
  the map, and it treats all distant tiles equally. Attention would let a unit on one continent directly "see" a
  fleet approaching from another continent — exactly the kind of long-range strategic awareness that matters in a
  Civilization game.

## 1.8 Related Projects and Known Bottlenecks

### Common Bottlenecks in Civ-Like RL Projects

1. **Credit assignment over long horizons** — a move now pays off 50 turns later.
   Mitigations: n-step returns, reward shaping, shorter games during early training,
   curriculum learning.

2. **Strategy cycling** — A beats B, B beats C, C beats A, training oscillates forever.
   Mitigation: opponent pool, Elo tracking.

3. **Massive action space** — many possible actions per turn.
   Mitigation: action masking, factored action spaces.

4. **Slow environment** — training bottlenecked by data generation.
   Mitigation: vectorized environments (see Section 2).

### Related Open-Source Projects

| Project | What It Is | Key Takeaway |
|---------|-----------|--------------|
| **CivRealm** (bigai-ai/civrealm) | Full Civ RL environment based on Freeciv | Even modern RL struggles with full Civ. Simplified versions (like Civulator) are the right approach. Reward shaping and curriculum learning were essential. |
| **MicroRTS** (santiontanon/microrts) | Simplified RTS for RL research | PPO with action masking and reward shaping significantly outperformed basic DQN |
| **LuxAI** (Kaggle competition) | Simplified strategy game competition | Top solutions used imitation learning from rule-based bots + RL fine-tuning, much faster than pure RL |
| **Griddly** (Bam4d/Griddly) | Custom grid game framework for RL | Handles rendering, vectorized envs, action masking. Could be used as environment framework |
| **alpha-zero-general** (suragnair) | Clean AlphaZero for custom board games | You'd write a CivulatorGame class. Best architecture for 2-player board games |

### Imitation Learning Bootstrap (from LuxAI insight)

An underrated approach: write a simple rule-based bot (attack nearest enemy, build
warriors when no threat, build settlers when safe), train a neural network to
imitate it via supervised learning, then fine-tune with RL. This gives the RL agent
a much better starting point than random initialization.

## 2.2 NumPy Vectorization

Replace Python loops over hex cells with bulk NumPy operations. This is the
**first thing to try** after profiling.

### Hex Adjacency (all hexes at once)

```python
# Axial coordinate system — 6 direction vectors
DIRECTIONS = np.array([[1,0], [1,-1], [0,-1], [-1,0], [-1,1], [0,1]])

# All hex positions as Nx2 array
hexes = np.array([[q, r] for q in range(W) for r in range(H)])

# All neighbors of ALL hexes at once: shape (N, 6, 2)
all_neighbors = hexes[:, None, :] + DIRECTIONS[None, :, :]
```

### Hex Distance (vectorized)

```python
def hex_distances(origin, targets):
    """origin: (2,), targets: (N, 2) — axial coords"""
    dq = targets[:, 0] - origin[0]
    dr = targets[:, 1] - origin[1]
    ds = -dq - dr
    return np.max(np.abs(np.stack([dq, dr, ds], axis=1)), axis=1)
```

### State Tensor Construction

If the game board is stored as numpy arrays from the start (terrain, units,
ownership — all shape (H, W) or (C, H, W)), then state tensor construction is
just `np.stack()` — essentially free.

### Precomputed Distance Tables

For small grids: compute all-pairs hex distances once as a numpy matrix.
32x32 for 4x8, 512x512 for 16x32 — trivial to store and compute. - Note from erik: I have a distance function that calculates distance on hex tiles- it's totally trivial. I forget the exact formula but it's composed of calculating two deltas of ints, then taking the max of them or something like that. 

**Expected speedup**: 5-20x overall, depending on how much time is in Python loops
that can be vectorized.

## 2.4 Vectorized Environments

Run N copies of the game in parallel. The GPU is idle during simulation and the CPU
is idle during inference — parallelizing overlaps them.

### Gymnasium AsyncVectorEnv (Recommended)

```python
import gymnasium as gym

def make_env():
    return CivulatorEnv()

# Each env in its own subprocess — true parallelism
vec_env = gym.vector.AsyncVectorEnv([make_env for _ in range(8)])
obs, info = vec_env.reset()
obs, reward, terminated, truncated, info = vec_env.step(actions)
```

### Stable-Baselines3 SubprocVecEnv (Alternative)

```python
from stable_baselines3.common.vec_env import SubprocVecEnv
vec_env = SubprocVecEnv([make_env for _ in range(8)])
```

**Expected speedup**: Near-linear scaling up to CPU core count. With 8 cores: ~6-8x
throughput. Combined with batched GPU inference: GPU utilization goes from ~10% to
~60-80%.

**Effort**: Low — works out of the box if your env follows the Gymnasium API.
**This is the single highest-impact change for training throughput.**

## 2.5 Cython, C++, PyPy

### Cython
Similar speedup to Numba (50-150x) but requires separate .pyx files, a compilation
step, and type annotations. More verbose. Better than Numba when you need to speed
up code that mixes Python objects with numerical work.
**Verdict**: Use Numba first. Cython if Numba can't handle it.

### C++/pybind11
100-500x vs pure Python, but essentially writing the game twice. Only worth it if
you scale to very large grids or need >100k episodes.
Look at **OpenSpiel** (github.com/google-deepmind/open_spiel) for architecture reference.
**Verdict**: Not yet. Revisit at Phase 4 if needed.

### PyPy
PyPy and PyTorch are not compatible. Separation via IPC is possible but adds
complexity. Numba gives similar speedups without the headaches.
**Verdict**: Not recommended.

## 3.6 RL Training Integration

### Key Principle: Never Render During Training

```
Training Loop (fast, no rendering)
    |
    +---> [State Logger] ---> replay.jsonl    (always)
    +---> [Optional Live Viewer]              (separate process, socket/queue)
```

### Best Practices

1. **`render_mode` parameter** (Gymnasium convention):
   - `None` — no rendering, maximum speed
   - `"human"` — open window, real-time
   - `"rgb_array"` — return numpy array (for recording)
   - `"ansi"` — ASCII (your current mode)

2. **Replay files** — log game state to JSONL each turn. Separate replay viewer
   reads these. Completely decouples training from visualization. Rewind, pause,
   overlay analysis.

3. **Separate process viewer** — use `multiprocessing.Queue` or ZMQ. Training

## 3.7 Hex Grid Rendering

### Canonical Reference
Red Blob Games' "Hexagonal Grids" guide (redblobgames.com/grids/hexagons/) is the
single best resource for hex math.

### Pointy-Top (Civ Convention, Recommended)

```python
import math

def axial_to_pixel(q, r, size):
    x = size * (math.sqrt(3) * q + math.sqrt(3)/2 * r)
    y = size * (3/2 * r)
    return x, y

def hex_vertices(cx, cy, size):
    angles = [math.radians(60 * i - 30) for i in range(6)]
    return [(cx + size * math.cos(a), cy + size * math.sin(a)) for a in angles]
```

### Cylindrical Wrapping (Visual)
- **Option A**: Duplicate 1-2 edge columns on each side, teleport camera at edge (what Civ games do)
- **Option B**: Draw flat, mark the edges (simpler, fine for debugging)
- Start with B, upgrade to A later.

### Python Hex Libraries
- **hexy** (PyPI): numpy-integrated hex grid, batch coordinate conversion
- **Roll your own**: The math is ~50 lines and lets you match your exact conventions

## 3.8 Recommended Phased Approach (Eriks comment: I would skip directly to pahse2)

**Phase 0 (current):** ASCII rendering in terminal.

**Phase 1 (1-3 days):** Matplotlib static renderer. Single game state to figure.
`RegularPolygon` patches for hexes, colored by terrain. Units as markers. Save
frames as PNG, stitch into replay videos. Immediate visual debugging, zero new deps.

**Phase 2 (3-7 days):** Pygame real-time viewer. Hex tiles, unit sprites (start with
colored circles), city markers. Keyboard pan/zoom. Separate `Renderer` class taking
game state snapshots. Follow Gymnasium `render_mode` convention.

**Phase 3 (optional, later):** Polish Pygame (sprite art, animations, RL metrics
overlay) OR build browser-based viewer for remote viewing.

**Across all phases**: Use the replay file approach. Log states to JSONL every turn.
This is the single most valuable architectural decision for RL debugging.
